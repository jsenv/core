# Texts and i18n

Every text an app displays is a value it owns, like any other. The goal here is
that those values live somewhere findable and are written as whole sentences —
not cut into JSX fragments, not concatenated at the call site, not scattered so
widely that changing the tone of the app means grepping for punctuation.

Translation is a consequence of doing that, not the reason to do it. An app with
one language still benefits from one place holding its wording; and once it does,
adding a second language becomes a data change instead of a refactor.

Four tools, from smallest commitment to largest:

| Tool                    | Gives you                                |
| ----------------------- | ---------------------------------------- |
| `interpolateText(t, v)` | one readable sentence with values in it  |
| `<Interpolate>`         | the same, with JSX allowed in the values |
| `createI18n()`          | a registry of the app's texts            |
| `naviI18n`              | navi's own texts, to override            |

Reach for `interpolateText`/`<Interpolate>` as soon as a sentence has a value in
it, and for `createI18n` as soon as more than a handful of texts exist — the
migration from the first to the second is wrapping the string in a call, which
is why starting with plain interpolation costs nothing.

## Writing a sentence: `interpolateText` / `<Interpolate>`

Use these the moment a sentence contains a value. They need no i18n instance and
no setup, so there is no reason to avoid them in a single-language app.

```js
import { interpolateText } from "@jsenv/navi";

interpolateText("Deleting [name]…", { name: file.name });
```

In JSX, `<Interpolate>` keeps the sentence readable when part of it is styled:

```jsx
<Interpolate radiusKm={<Text bold>{radius} km</Text>} zoneName={zone}>
  Data limited to [radiusKm] around [zoneName].
</Interpolate>
```

The point is that the full sentence is visible in one place. The alternative —
`Data limited to <Text bold>{radius} km</Text> around {zone}.` — reads as
fragments, and cannot later become a translation key, because there is no
single string to be the key. Placeholders are `[name]`; what a value can be (a
dot-path, a function) and what a missing one does are in `interpolateText`'s
JSDoc.

## Centralizing texts: `createI18n`

Once several components display text, give the app a registry. One instance for
the whole app, exported from one module:

```js
// src/app_i18n.js
import { createI18n } from "@jsenv/navi";

export const i18n = createI18n({ keyLang: "en" });
```

Then call it wherever a text is needed. It is callable directly:

```js
import { i18n } from "@/app_i18n.js";

i18n("Deleting [name]…", { name: file.name });
```

A placeholder's value is data — a name, a number, a formatted date — or wording
the code picks: "tonight", a label from a table. Wording is looked up too, and
handed over translated; so is a unit word of the app's own, which `<Quantity>`
shows as given:

```jsx
i18n("Updated [when]", { when: i18n("tonight") });
<Quantity unit={[i18n("ticket"), i18n("tickets")]}>{count}</Quantity>;
```

### In an app, the text is the key

`keyLang: "en"` means "keys are already written in English". The key doubles as
its own English template, so a single-language app registers nothing at all and
still gets readable output, and adding French later touches only the registry:

```js
i18n.add("Deleting [name]…", { fr: "Suppression de [name]…" });
```

This is the recommended style for applications, because it keeps the call site
readable. `i18n("Deleting [name]…")` says what appears on screen;
`i18n("file.delete.progress")` requires a lookup to know. The cost — changing
the English wording changes the key, so its translations must be updated
alongside — is the smaller problem in practice, and it is a mechanical one.

### In navi, the key is opaque

`naviI18n` uses opaque keys (`"list.empty"`, `"constraint.required.email"`)
because a library's texts are addressed from the outside: an app overriding a
message needs a stable name that does not move when navi rewords its default
English. Same reasoning applies to any shared component library — the trade-off
flips with who owns the text.

A key no language translates comes back as is, so a missing translation
degrades to readable text rather than blank space or a crash — with opaque keys,
to the key's name. That is why an instance with opaque keys wants a
`fallbackLang` holding every key (`naviI18n` falls back to English), and
`i18n.has(key)` is how to tell "no translation" apart from "a translation that
happens to equal the key". Registering (`add`, `addAll`, `addLangKeys`) and how
the language is resolved key by key are in `createI18n`'s JSDoc.

## A sentence that depends on a number

A sentence whose words follow a count is one translation with several forms,
never two keys picked in code with one language's rule baked in (`count > 1 ?
plural : singular` is wrong in French at 0 and in English at 0, and Polish has
three forms where English has two). The forms go in place of the string, and
`count` picks one: an exact number written as a key first, then the form the
language gives that number (`Intl.PluralRules`), then `other`:

```js
const seats = {
  0: "Full",
  one: "[count] free seat",
  other: "[count] free seats",
};
i18n(seats, { count: place.freeSeats });
```

The `other` string is the key the other languages register their forms under —
each language with the forms it has:

```js
i18n.add("[count] free seats", {
  fr: {
    0: "Complet",
    one: "[count] place libre",
    other: "[count] places libres",
  },
});
```

With opaque keys, every language registers its forms under the key, and the
call passes `count`: `naviI18n` does this for its own messages. `<Quantity>`
picks its unit's form by the same rule, and `pluralCategory(count, { lang })`
answers it for a choice that is not a sentence.

A list of items read as one phrase is joined by `formatList` — the language's
"and" or "or" and its commas ("8h–10h, 12h et 18h–20h"), never a hand-written
`" et "`.

## Which language

Nothing needs configuring for navi and app texts to agree on a language: both
default to `languagesSignal`, which is read live on every lookup — the browser's
`navigator.languages`, plus two app-level overrides.

```js
import { setSupportedLanguages, setPreferredLanguage } from "@jsenv/navi";

setSupportedLanguages(["en", "fr"]); // what the app offers, at startup
setPreferredLanguage("fr"); // what this user picked, from a language picker
```

`setSupportedLanguages` matters more than it looks: without it, a browser
preferring German reads German wherever German exists — navi's time wording,
every date and number — and the next language it lists, or English, for the
rest: navi's buttons and messages, the app's own texts. One page, two
languages. With it, that browser lands on the app's best available language for
all of them.

It decides more than the wording: `<Time>` and the format helpers
(`formatNumber`, `formatTime`, …) read the same signal, so **a document that
never calls it follows the browser, dates and numbers included** —
`2026-09-01` reads "09/01/2026" on an en-US machine and "01/09/2026" on a French
one, from the same code and the same data. Nothing on screen says which reading
is being applied, so this is worth one call at startup even in an app with a
single language, and in every document of the repo (an admin panel, a demo
page), each of which starts from zero.

Because the language is read at lookup time, a component that reads `i18n(...)`
during render re-renders with the new wording when the language changes — as
long as the call happens in render, not in a value captured once outside it.

## Writing a value

A number, a day or a time on screen is wording as much as a sentence is, and
navi writes it: never `Intl` or `toLocale*` with a locale of the app's own,
which pins one region beside navi's dates and ignores `setSupportedLanguages`.
Each helper takes `lang` and otherwise reads the signal above; the component is
for JSX, the function for a string (a `title`, a notification).

| Value                           | Component                                          | String                                           |
| ------------------------------- | -------------------------------------------------- | ------------------------------------------------ |
| a number                        | `<Quantity>`                                       | `formatNumber`                                   |
| a size in bytes                 |                                                    | `formatByteSize`                                 |
| a day                           | `<Time type="date">`                               | `formatDay`                                      |
| a month                         | `<Time type="month">`                              | `formatMonth`                                    |
| a day and its time              | `<Time type="datetime">`                           | `formatDatetime`                                 |
| a time of day                   | `<Time type="time">`                               | `formatTimeOfDay`, or `formatTime` from a `Date` |
| a clock from a count            | `<Time type="hour"\|"minute" format="timestring">` |                                                  |
| two times of day                | `<TimeRange>`                                      | `formatTimeRange`                                |
| a day relative to today         | `dayLabel` on `<Time type="date">`, beside the day | `formatDayRelative`                              |
| an instant, from now            | `<Time type="relative">`                           | `formatTimeRelative`                             |
| a duration                      | `<Time type="duration">`                           | `formatDuration` and its per-unit siblings       |
| the time elapsed since, ticking | `<Time type="duration" since={instant}>`           |                                                  |
| items read as one list          | `formatList` over elements                         | `formatList`                                     |

A spelled day writes its year only when it is not in `now`'s year (`year:
"auto"`, see `formatDay`): appending the year by hand writes it twice for a
date in another year. A capital letter at the start of a value is
`<Text capitalize>`, not a sliced string.

The shape of a number is asked of `formatNumber` too: it takes
`Intl.NumberFormat`'s options in the reader's language — a fixed precision
(`formatNumber(seconds, { minimumFractionDigits: 1, maximumFractionDigits: 1 })`
→ "1,0"), a sign (`signDisplay: "exceptZero"` → "+3") — and `<Quantity>`
forwards the fraction digits and the sign. A time written to the second (a log
line, a "checked at") is `precision: "second"` on `formatTime`,
`formatDatetime`, `formatTimeOfDay` and `<Time type="time"|"datetime">`.

A list whose items are elements — a `<TimeRange>` per span — goes through
`formatList` as well: given an element, it returns a fragment with each element
at its place between the language's words, where a hand-written " et " would
join them in one language only.

## Changing what navi says

`naviI18n` holds navi's own texts. Register on it to override a default or to
add a language navi does not ship:

```js
import { naviI18n } from "@jsenv/navi";

naviI18n.add("list.empty", {
  en: "Nothing here yet.",
  fr: "Rien pour l'instant.",
});
```

Its JSDoc lists the key namespaces and the unit names `<Quantity>`/`<Unit>`
look up; the exhaustive list of keys and defaults is the registration block in
`src/text/navi_i18n.js`, plus the `time.*` wording the formatters use,
registered by `@jsenv/humanize`. Both go into the one registry `naviI18n` is,
so overriding either is the same call.

A key whose default holds forms — a message that counts characters, actions,
line breaks — is overridden with forms too, or the one string is said whatever
the count:

```js
naviI18n.add("constraint.min_length.default", {
  fr: {
    1: "Au moins [min] caractères (un seul pour l'instant).",
    other: "Au moins [min] caractères ([count] pour l'instant).",
  },
});
```

**Do not put application texts in `naviI18n`.** Key collisions aside, the two
have different lifecycles: navi's keys come with the package version, the app's
come with the app. The unit names it looks up are for rewording a unit navi or
`Intl` already knows ("hour", "kilometer"); a unit word of the app's own comes
from the app's registry, translated (see [above](#centralizing-texts-createi18n)).
